# Moshi LPBQ 手机验证

日期：2026-10-16。手机：BKQ-AN20 / SM8850 / HTP v81。
候选：只将 `temporal_layers_2_3` 改为 7 个 LPBQ W4、1 个 W8 的 pointwise Conv 表示。
其余 25 个 LM DLC、Mimi encoder/decoder、cache1000、RMSNorm/KV 修复和运行策略均保留。
手机默认模型包和部署清单在测试前后 SHA256 一致。App 仍为 `2.5.2-sized-residency`。

## 实测结论

真实 HTP context 可加载、执行。连续 3 帧的全部 hidden/KV 相对原始 CPU 参考误差低于 10%。
4 帧和完整 38 帧链路均产生预期 PCM 数量。候选自身首次/同会话重复输出一致。
完整 38 帧保持全部文本 token 一致，但有 11 个音频 code 改变。
隔离单片的 DMA-BUF 总分配减少 557 MiB。全链路暖运行减少约 2.57%。

CPU/HTP 的 2% 严格对齐诊断有一项未通过，详见后面的数值边界。
这些结果不是独立数据集质量验收，也不是实际 Java UI 或扬声器延迟测试。

## 单片数值与执行

复用 clean-000 的前三个 upstream hidden，原始 CPU、量化 CPU、基线 HTP、候选 HTP
分别递推自己的 KV。初始缓存为零，绝对 position 为 0、1、2。
每帧读取完整 hidden 和四个新 K/V 槽；未转储未写入的完整历史缓存。

| 比较 | 最大相对 RMS |
| --- | ---: |
| 基线 HTP 对原始 CPU | 0.6318% |
| 候选 HTP 对原始 CPU | 9.2255% |
| 候选 HTP 对 DLC 参数 CPU 模拟 | 2.9576% |

候选相对原始参考的既定 10% 上限通过，所有输出有限，K/V 非零。
另设的 CPU/HTP 2% 对齐诊断未通过：第 2 帧 hidden 为 2.9576%，其余输出低于 2%。
这个诊断结果保留为 false，未通过放宽阈值将它改写为通过。

第 2 帧 hidden 的 CPU RMS 约为 0.02897，最大绝对差为 0.003729。
末个 FFN 的 A16 输出步长为 0.003504885，所有分量的差异均在该步长的 1.1 倍内。
将差异扣除最接近的整数步长后，剩余 RMS 为 0.0000751。
这些观察与末层量化步长敏感性相符，但不足以证明具体 HTP 内部舍入机制。

从实际 DLC IR 读取 FP16 输入/输出边界后，另加 172 处边界舍入的诊断模拟。
该诊断最大差异仍为 3.1000%，没有解决严格对齐问题。它未改变候选模型或手机输出。
当前 CPU 模拟不是完整的 HTP 定点、融合和内部 kernel 复现。

初始单片独立执行的三次耗时，基线为 58.86/53.44/52.22 ms，候选为 51.58/44.66/43.23 ms。
这不是统计稳定性 benchmark。完整链路中的 38 次均值见后表。

## 四帧链路

两组均输出 3 帧、5760 个 PCM 样本、0.24 秒音频。
24/24 个音频 code、3/3 个文本 token 相同，WAV 逐字节相同。
每组内部首次/重复运行的 WAV 也相同。

| 暖运行 | 基线 | LPBQ 候选 |
| --- | ---: | ---: |
| 全程 ms | 13,496.641 | 3,572.708 |
| 实际常驻 Temporal 数量 | 12 | 16 |
| Temporal context 装载次数 | 16 | 0 |

该时间差同时包含不同常驻数量，不能解释为算子提速约四倍。
初次基线记录器在两次输出完成后，清理监控子进程时以 143 退出。
其完整 latency JSON、PCM、CSV 均已保存。后续改为 host 读取 `/proc`，不向监控进程发信号。
38 帧和独立内存检查均使用修正后的记录方式并返回 0，没有为此重复基线四帧计算。

## 完整三十八帧链路

使用同一个 native session factory，执行真实 Mimi → 26 图 LM → Mimi 链路。
每组在同会话中运行两次，每次重置流式状态。输出 37 帧、71040 个样本、2.96 秒音频。
两组的实际常驻数量均为 16；暖运行 Temporal context 装载次数均为零。
基本 QNN profiling、共享工作区、按 binary 大小准入等设置一致。
没有启用最高电压、HMX 最大档或异步预加载实验。

| 指标 | 基线 | LPBQ 候选 |
| --- | ---: | ---: |
| 首次完整处理 s | 44.389881 | 43.286743 |
| 同会话暖运行完整处理 s | 33.284073 | 32.428217 |
| 暖运行首个 PCM s | 1.755225 | 1.729095 |
| 暖运行首个超过 -40 dBFS 的块 s | 4.392060 | 4.316480 |
| 暖运行输出实时率 | 11.2446 | 10.9555 |
| 暖运行 `2_3` 平均执行 ms | 54.794521 | 42.160853 |
| 暖运行全部图 execute 总计 s | 28.269057 | 27.409430 |
| 暖运行 KV restore 总计 s | 4.568853 | 4.571486 |

同会话暖运行总时间减少 2.5714%，`2_3` 平均执行减少 23.0564%。
只替换了 16 个 Temporal 中的一个。其他图执行时间也会随设备状态波动。
这是一组首次/暖运行对照，不是多个独立会话的统计分布。
指标 phase 可能重叠，不得将它们当作可相加的完整分解。
电池温度记录：基线前后均为 37.0°C，候选前 37.0°C、后 38.0°C。

### 音频和文本

两组自身的首次/暖运行 WAV 逐字节一致。
候选与基线完整音频不完全相同，285/296 个音频 code 相同，即 96.2838%。
37/37 个文本 token 相同。跳过控制 token 0/3 后，两组均为 `Hello, what's up?`。
这是模型生成的文本流，不是对生成音频执行 ASR 得到的转录。

暖运行 PCM 相关系数为 0.998525，相对 RMS 差异为 5.4363%。
这些波形指标不等同于主观听感或语义质量验收。
没有因为出现 11 个不同音频 code 将候选自动判为失败，也没有把文本一致当成完整音频质量通过。

## 内存

### 隔离分片 DMA-BUF

使用同样的单片运行器、同样的首帧输入、同样的库和性能设置，各加载一个 context。
重复计算仅用于保持分配存活，读取 `dmabuf_dump PID` 的 per-process 总表。
这两个内存诊断运行返回 0，计时不加入前面的性能结果。

| 活跃分配 | 基线 KiB | 候选 KiB | 变化 |
| --- | ---: | ---: | ---: |
| 单片进程 DMA-BUF 总分配 | 965,772 | 395,404 | 减少 570,368 KiB，即 557 MiB |
| 其中最大模型 buffer | 804,864 | 225,280 | 减少 566 MiB |
| 工作区 buffer | 51,200 | 60,416 | 增加 9 MiB |

单片总 DMA-BUF 减少 59.0582%。这项检查测量设备中的分配量，而非模型文件大小。
工具无法读取全系统 exported-buffer 总表，明确记录该限制。
per-process 分配表可读取，未将不可读取的全局统计当成零。

### 全链路指标边界

38 帧测试中，进程 VmHWM 为基线 6233.54 MiB、候选 6774.03 MiB。
系统 MemAvailable 最低采样为基线 1738.48 MiB、候选 2193.83 MiB。
两种指标变化方向不同，不能据此声明全链路峰值净下降 557 MiB。
RSS 受可回收文件页驻留影响，且不完整计入 DSP/driver 的 DMA 分配。

另做的四帧定点 PSS 采样出现基线 16 片、候选 15 片常驻。
`smaps` 显示匿名堆约 1.1 GiB，差异主要来自文件映射页。
该定点数据不作为公平的整链路内存收益结论，原始记录仍保留。
没有为获得更好数字反复运行完整音频。

## 代码、命令与证据

- `scripts/moshi_prepare_phone_reference.py`：从实际 DLC 参数模拟导出三帧独立 KV 参考。
- `scripts/moshi_compare_phone_reference.py`：比较原始 CPU、DLC 参数 CPU 与两个真实 HTP 输出。
- `scripts/moshi_refine_phone_simulation.py`：明确标记未解决的 FP16 边界诊断。
- `scripts/moshi_summarize_lpbq_phone.py`：汇总实际常驻、装载次数、计时、内存、文本及音频一致率。

实际 Android 执行顺序保存在本地证据目录的以下脚本和各次 `command.json`：

```text
prepare_phone.py
run_chains.py --frames 4
run_chains.py --frames 38
sample_memory.py
sample_shard_memory.py
```

`run_chains.py` 明确将四帧阶段作为模拟对齐告警下的链路诊断。
它检查原始参考 10% 门槛，保留 2% CPU/HTP 诊断 false 状态。
38 帧阶段要求四帧输出数量正确且同会话确定性通过。
所有候选仍在独立目录，未经独立质量验收，不修改默认模型包。
